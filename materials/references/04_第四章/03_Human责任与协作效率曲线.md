## 从 Flow 效率回到人的理解

2026-07-28，Humanize 作者总结了一次个人工作方式变化：实现型任务中，
先与模型讨论到自己也能动手，再让 Agent 一次完成，常常比继续叠加 Flow
更快；探索型任务仍然需要 Flow 帮助形成理解。他后来把“想清楚”解释成
“我上我也行”，没有要求人在动手前预知所有细节。

## 动态主义与组合主义

2026-08-02，群聊重新比较三种路线：

- Humanize 1.0 的固定、已验证 Flow；
- Claude Code Dynamic Workflows 的阶段、循环与并行组合；
- Codex `ultra` 按当前状态在线派发 Subagent。

社区将后两种倾向概括为组合主义与动态主义。机械式维护适合代码化
Flow；需要频繁介入、不断出现新信息的探索任务更适合现场判断。固定
Flow 无法预见后续所有问题，在线调度也会出现主 Agent 大包大揽、
Subagent 过度递归等故障。作者当时仍靠手动切换两种模式，并明确说
自动平衡机制尚未找到。

## 效率曲线的证据边界

第四章的[协作效率曲线](../../figures/11_第四章_Agent协作效率曲线.svg)来自
笔者提出的概念模型：

1. 直接引入 Agent 后出现局部效率高峰；
2. 返工、目标漂移、过度设计、协调成本和认知债使效率下降；
3. 任务适配的 Harness 加上以人为核心的协作机制，使效率再次上升；
4. 预期第二次上升的斜率超过传统开发。

当前聊天记录提供了每个阶段的体验和失败案例，没有统一统计口径，也
没有一组数据能画出真实曲线。图中纵轴无量纲，不应补造百分比。后续若
要验证，可记录端到端交付周期、返工比例、逃逸缺陷、维护工时、Human
Review 时间与客户验收结果。
