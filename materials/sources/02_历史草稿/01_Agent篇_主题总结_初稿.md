# 当 Agent 开始组成团队

## Humanize 社群关于 Agent、Harness 与 Flow 的持续讨论

三月下旬，群里先后出现了两条看上去互相矛盾的消息。

一条是：“我有 76% 的自信认为 Agent Teams 是个无用设计。”另一条是：一次启动 22 个 Agent，三个多小时完成了 4.7 万行代码增量，并且第一次编译就通过。

这两句话其实指向了同一个问题：**多 Agent 的关键从来不是“多”，而是它们如何被切分、隔离、约束、审查和停止。** 被质疑的是 Agent 之间自由交谈的团队模式，而不是并行本身；被认可的是有明确任务、独立上下文、隔离工作区和集中汇总的并行执行。

接下来几个月，Humanize 社群围绕这个问题反复试验。讨论从 Agent Teams 与 Sub-agent 之争，走到 PDBR、Harness、Agent Flow 编程语言、记忆系统、人类在环，再走到模型主动调用几十乃至上百个子 Agent，以及模型逐渐把既有 Harness “内化”之后，外部工作流是否还需要存在。

这不是一套已经定型的方法论。它更像一份不断被真实项目修正的现场记录。

>
> 本文只依据社群聊天记录整理。原始材料来自 OCR，存在错字、重复、消息错位和署名粘连的可能，因此正文主要以“有群友”“参与者”“Humanize 作者”转述，不强行给每句话署名。文中的代码量、Agent 数量、运行时长、Token 消耗和效果比较，均是群友在具体项目中的个人报告，不是经过统一条件复现的 Benchmark。记录中没有解决的争议，本文也不替它补上答案。

## 一、这里说的 Agent，已经不是一个聊天机器人

讨论早期，群友曾尝试用管理学比喻多 Agent：老板、经理、小兵、公司、三省六部。但随着实践增多，大家越来越发现，这类比喻容易把人的组织经验原样投射到 Agent 上，反而遮住真正需要设计的东西。

四月的一次讨论给出了一个更工程化的表达：

> `Agent = Model × Tool × Action × Permission`

模型只是其中一部分。一个 Agent 能做什么，还取决于它拿到什么工具、允许采取什么动作、具有什么权限。群里也有人把最终结果写成：

> `Result = Model × Tool × Flow`

这两个式子未必是严格的数学关系，但它们很好地概括了群里的共同经验：换一个模型会改变结果，换一套工具会改变结果，换一种 Flow 也会改变结果。不能把失败全部归咎于模型，也不能期待一套 Harness 把任何模型都“抬”到同一水平。

因此，社群讨论里的 Agent，通常指的是一个处在具体工程环境中的行动单元：它能读哪些上下文，能调用哪些工具，能否修改代码，能否启动子 Agent，能否访问网络，能否给别的 Agent 发消息，产物写到哪里，由谁验收。所谓 Agent 系统，实际是在设计这些行动单元之间的边界和控制关系。

## 二、先把人的意图变成一个可以执行、可以验收的东西

最初的 Humanize 实践，核心并不是“让 AI 自己想办法”，而是把人的意图逐步变成可执行的计划。

群里很早就对模糊许愿保持警惕。循环可以让实现越来越完整，却不保证它会自动获得全局视角，也不保证它能发现训练分布之外的新洞见。自然语言本身有歧义；如果目标、边界和验收标准没有讲清楚，多轮迭代也可能只是沿着一条错误路线越走越深。

这套思路后来被概括为 PDBR：

- P，Plan：承载人的意志和目的。

- D，Delegate：决定任务能被切到多大、每个执行单元是否拿得到合适的上下文。

- B，Build：影响完成任务的收敛速度。

- R，Review：影响最终收敛的质量。

当时给出的“最简单可行架构”是：

> `P - /loop { D - /batch { B - R } }`

外层循环让任务逐步收敛；每一轮先做委派，再并行执行若干彼此隔离的 Build—Review 单元。

这套表达里有几个后来反复出现的原则。

第一，Plan 不是实现代码的仓库。计划阶段要保留目标、约束、依赖、边界和验收标准，把具体实现决定留到真正执行时。群里甚至把“Plan 禁止写 Code”与“干活的小兵禁止沟通”并列为两条戒律。

第二，Build 和 Review 不应完全由同一个上下文完成。执行者已经在某条路径上投入了大量上下文，容易替自己的方案辩护；一个没有经历实现过程的审查者，反而更可能看到隧道视野之外的问题。讨论中多次出现“拉一个无上下文 Reviewer”的做法。

第三，Review 不是越密越好。给每个很小的 Worker 都套一层完整审查，会让系统过早陷入局部打磨；只在最顶层统一审查，又可能因为改动过大而遗漏问题。审查粒度要跟任务结构一起设计。

第四，计划是否固定，没有一直保持同一个答案。早期 Humanize 强调执行期间不要修改 `plan.md`，避免目标漂移；后来 `/goal` 和动态工作流兴起，群里又开始追求渐进式规划。两者的分歧不是“要不要计划”，而是：计划里的哪些部分必须稳定，哪些部分可以随着新证据更新，以及谁有权修改它。

## 三、“不沟通”不是不协作，而是把协作变成可见的产物

Agent Teams 是整段记录里争论最久的主题之一。

反对自由通信的一方认为，干活的 Worker 通常只需要把自己的任务完成，并不需要互相聊天。平级消息会制造几类问题：

- Leader 看不到 Worker 之间发生了什么，无法判断某个决定从哪里来。

- 消息到达时可能已经过时，接收方却会把它当成新事实。

- 多个 Agent 重复阅读、重复解释，消耗上下文并引入噪声。

- 一个 Agent 的错误经验可能通过对话污染其他 Agent。

- Leader 自身的 Context 和 I/O 会成为瓶颈，但加入更多沟通层级未必能解决，反而可能增加压缩损失。

由此出现了整段讨论中最有代表性的一句话：

> 难的其实并非如何让任意两个 Agent 沟通，难的其实是如何让两个 Agent 禁止沟通。

“禁止沟通”也不应只写在 Prompt 里。群友很快把它推进到权限层：Planner 不拿写代码工具，Worker 不拿给同伴发消息的工具；与用户对话的主 Agent 可以只负责委派；不同 Worker 使用独立 Worktree；结果统一写入文件，再由 Manager 显式整理和转交。

一个相对安全的拓扑是：多个独立专家分别读取任务并产出结果，Manager 汇总，再决定是否把上游结论交给下游。Agent A 的输出如果要成为 Agent B 的输入，最好经过一次可见的编排，而不是在 Leader 不知情时直接传递。

但记录也没有把“禁止沟通”写成无条件真理。群里至少提出了几类例外：

- 跨代码库工作时，另一个 Agent 可能持有当前 Agent 无法直接读取的上下文。

- 长任务之间需要 Handoff 时，文件、脚本、论文或其他结构化产物可以承担通信协议。

- 经过环境验证的发现，可以放进共享的任务产物中，供其他 Agent 使用。

- 探索、Brainstorming 和多视角研究，有时需要真正不同的假设相互碰撞。

真正逐渐稳定下来的区分，不是“沟通或不沟通”，而是**对话式通信与产物式通信**。前者即时、模糊、难追踪；后者较慢，却能审查、复用、回滚和交接。五月以后，“以产物为中心”不断取代“以对话为中心”，成为讨论 Flow 时常见的判断标准。

七月，多人多 Agent（MHMA）开始进入实践。有人把协作方式分成单人单 Agent、单人多 Agent、多人单 Agent、多人多 Agent。一个很具体的交接方法是：我方 AI 写一键脚本，对方 AI 读取这个脚本并接手后续工作。这里仍然没有让 Agent 自由开会，人的协作也被压缩进了一个可检查的交付物。

## 四、并行的本质是 Context Engineering

群里多次把 Sub-agent 理解成一种上下文隔离工具，而不只是“多一个劳动力”。主 Agent 把一个边界明确的任务交出去，子 Agent 在新上下文中完成探索，再把结果压缩回来。这样做有三种价值：

- 主上下文不必装下所有中间搜索过程。

- 多个 Agent 可以从不同起点独立尝试，减少初始方案造成的路径偏置。

- 执行与审查可以发生在彼此独立的上下文里。

三月的一次个人实践中，参与者先用一周时间交互式搭出约八万行的 MVP，再把“从 1 到 100”的扩展任务拆成一个 Master Plan 和 21 个小 Plan，每个小 Plan 对应约一千到三千行的增量，随后用隔离的 Batch 并行执行。这个例子支持的是“成熟设计之后的横向扩展可以被大规模并行”，并不能推出“任何项目都适合一次开 22 个 Agent”。群里自己也强调，21 个 Plan 是人看过的，Master Plan 只描述并行度和依赖，任务性质也已经从探索变成了扩展。

到了七月，模型会主动启动 10 个、23 个、70 个乃至 101 个子 Agent。Agent 数量不再需要人手工指定，管理负担明显下降；但新的问题立刻出现：

- 子 Agent 递归启动子 Agent，深度没有合理上限。

- 主进程与后台任务的生命周期可能错位，完成消息、停止 Hook 和任务状态难以统一。

- 同一项验证被父子 Agent 重复执行，成本急剧上升。

- UI 在累计数百个子 Agent 后变卡，生命周期难以观察。

- 一次 Deep Research 就可能消耗相当比例的周额度。

- 基础设施跟不上模型的派发速度，出现“烧了配额却没有完成工作”的情况。

这些现象把问题重新拉回控制面：并行数、递归深度、任务状态、停止条件、预算和异常回收都必须可见。Agent 的数量是结果，不是目标；“一直运行”也不等于“持续进展”。

Worktree 也不是完整隔离。群里有人报告，长对话运行一段时间后，Agent 会走进另一个 Worktree，看见其他任务的 Diff；Worktree 一多，合并冲突也可能反过来吞掉并行收益。实践中的补救包括：每个 Worktree 使用独立 Session、限制并行工作区数量、由人维护 Worktree 生命周期，以及一旦出现冲突就尽早合并。这里隔离的不只是一组文件，还包括 Session、进程与环境。

## 五、Harness 不是更长的 Prompt，而是一套控制系统

三月二十日，群里有人用一句话概括了后续几个月的大部分讨论：

> Harness 工程就是控制论。

这里的“控制论”主要是一种工程直觉，而不是把经典控制理论的数学结论直接搬到 Agent 上。Agent 是非确定性的，很多状态无法完整观测，也很难用一个连续数值描述“偏了多少”。但负反馈、部分观测、误差修正、稳定性、停止条件这些观念仍然有用。

一个 Harness 至少要回答几类问题：

- 目标是什么，怎样算完成？

- 每个节点能看到什么、能做什么？

- 哪些规则由模型理解，哪些规则由程序强制？

- 系统当前处在哪个状态，是否仍在推进？

- 失败后从哪里恢复，是否可以回滚？

- 谁能修改计划、代码、测试、记忆和 Flow 本身？

- 什么时候必须停下来找人？

聊天中不断出现同一个偏好：**简单、确定、机械的事情交给脚本、工具权限和 Hook；需要判断的事情交给 Agent；后果需要被承担的事情交给人。**

例如，“不允许 Planner 写代码”如果只是一句提示，它可能被忽略；直接不给写工具，边界会更硬。“遵守共享工具、不要猜数据结构”等黄金原则，如果只能靠每次提醒，就会漂移；编码成静态检查、测试和后台扫描，更容易持续执行。Reviewer 的结论也不应只是一段自然语言，可以进一步落为通过、拒绝、问题清单、日志路径或状态文件。

Humanize 自身的演化也被描述成一次长期做减法。作者回顾，自己曾设计过超过 60 个 Agent 的复杂交互系统，经历大量失败后几乎全部删除，只保留 Ralph Loop 与独立 Review。这个故事在群里被反复用来解释“Less is more”：复杂不是能力的证明，只有确实改变结果的结构才值得留下。

长任务还催生了 Monitor Agent。它与 Reviewer 不完全相同：Reviewer 检查阶段产物，Monitor 更关注时间流逝、主线是否推进、是否钻进细节以及什么时候需要升级给人。一次个人实践中，第三方 Agent 每小时读取另一个长程任务的 Transcript；发言者报告，约每十到十二小时会观察到一次它认为的偏离，并且会先等待数轮，确认任务没有自行恢复后再注入纠偏。这只是单个工作流的观测。后续讨论更谨慎地认为，Monitor 在多 Flow、长任务时有增量，在一两个短任务里未必值得；Monitor 与 Review 同时注入还可能造成 Hook 冲突。

隔离也从 Worktree 继续向运行环境推进。七月的讨论把 `tmux` 比作给 Agent 键盘，把 SSH、Kubernetes 与容器比作弹性沙箱，把 VNC 与 Computer Use 比作鼠标和显示器。对超长程探索，参与者尤其看重可 Snapshot 的 Sandbox：跑偏后可以退回几个快照以前，在同一环境中重新分叉，而不是从头开始。这里同样只是工程提案和早期实践，但它补上了 Git 难以覆盖的进程状态、依赖环境、外部副作用和 Reward Hacking 隔离。

但“简单”也不能退化成放任。记录后段的“星舰”和“船坞”梗，恰好说明了能力更强的 Agent 为什么仍需要边界：一个本来只需要“小船”的任务，模型可能把宇宙射线都当成 P0 Blocker，先造完整船坞，再建大量兼容层、清单、哈希、测试的测试和文档的文档。它在局部上很严谨，整体上却偏离了项目真正的收益与损失。

所以，Harness 的目的不是让系统永不出错，而是让偏离更早暴露，让人知道它为何做出某个决定，并能以较低成本停止、修正和重来。

## 六、从工作流到编程语言：h1、h2 与 h3

四月下旬，关于 Agent Flow 的讨论发生了一次明显转向：大家不再只把它当成一套 Prompt 或管理流程，而开始把它类比成编程语言、编译器与运行时。

当时的一组设想是：

- `humz`：描述 Agentic Flow 的语言。

- `hcc`：把描述编译成脚本和 Harness 的编译器。

- `hvm`：把编译结果与用户输入放到具体基础设施中执行的运行时。

在这套语言里，Codebase 可以被看作变量，Context 是隐藏值，Prompt 是谓词，State 是控制标签，Agent 是由模型、工具、动作和权限共同定义的算子。整个开发过程可以表示成数据流图；静态检查则可以寻找“永远不会触发的 Agent”、缺失依赖、不可达节点，以及类似组合逻辑回环的目标漂移。

讨论中还出现了两句很大胆的类比：

> LLM is the new processor/interpreter.  
> Agent Flow is the new code.

这条路线后来被概括为三个阶段：

- h1：一套已经能工作的 Flow。

- h2：由人设计、构建和测试 Flow 的平台或语言。

- h3：让 Agent 构建、选择甚至修改自身 Flow 的自动化系统。

h2 的价值不在于替用户自动找到最优工作流，而在于给 Flow 一组原语、运行环境和静态检查，让不同设计可以被表达、运行、比较和复现。h3 则进一步追问：谁来决定当前 Flow 不再适合任务？处在 Flow 内部的 Agent，是否有能力意识到支撑自己的结构需要改变？它能否申请暂停节点、修改 Flow，并在人类批准后继续？

一种自改进实验把“改 Flow”和“跑任务”分给两个 Agent：AI1 只能修改 Workflow、启动实验、记录每轮结果并分析原因；AI2 只能严格按照收到的 Workflow 执行。参与者特意用脚本、MCP 和模板把部分状态硬编码，因为仅靠自然语言要求 AI2 遵守流程，既容易失效，也会污染上下文。这个设计试图避免执行者一边参赛、一边改规则、一边给自己判分，但当时仍是实验，不是成熟方案。

这条路线始终伴随反对意见。

有人认为，自然语言顶层设计无法被过早形式化，DSL 只会制造新的复杂度；直接使用 Python、TypeScript 和 Agent SDK 已经足够。也有人担心，固定工作流会限制快速增强的模型，昨天有用的结构很快就会被模型能力吞掉。支持者后来也收缩了主张：Workflow as PL 首先是一种思维模型，真正实现未必要复用 LLVM、MLIR 或专用 DSL，关键是找到少量稳定、可检查的编排原语。

这套结构还有一个更靠近基础设施的延伸：如果运行时预先知道下一步会串行、循环还是并发十个 Agent，就可以把这些 Flow 信息交给推理服务做预加载、调度、缓存和模型路由。群里把它称为 Flow-aware Inference。记录中的这部分主要是研究设想，尚不能写成已经验证的系统收益。

记录末尾，群友发布了一个 Agent-Flow-Language 的早期版本，用 IR 表达复杂工作流，并明确说明对 Skill、MCP、安全和 RAG 的支持仍有限。这说明“Flow 作为程序”没有只停留在比喻上，但它是否比普通程序更适合作为 Agent 编排载体，记录中仍没有定论。

## 七、构建任务与探索任务，需要不同的 Flow

“构建”与“探索”的区分，从三月一直贯穿到记录末尾。

在构建型任务里，目标和验收标准相对清楚。Agent 更像约束求解器：给定一组硬约束、目标函数和启发式方法，在解空间里找到一个合法实现。这类任务适合较强的约束、清晰的任务切片、隔离执行、持续审查和机械验证。

在探索型任务里，问题本身还没有定型。过早写死 Flow，可能让所有 Agent 沿着同一个错误方向高效前进；过多共享记忆，也可能让独立探索失去多样性。群里有过一种实践：给九个 Agent 分配不同的大方向，比让九个 Agent 做同一个模糊任务更有价值。这里起作用的不是讨论，而是独立的假设空间。

因此，有人把两类 Flow 概括为：

- Build Flow：强约束、强 Review、较弱发散。

- Exploration Flow：强发散、弱一些的即时 Review，先保留多个候选方向，再比较和收敛。

“Build an exploration tool, not build tool while exploring”也在记录中多次出现。它表达的不是探索前必须把所有基础设施都造完，而是不要把“验证一个研究假设”和“顺手建设一套长期系统”混在同一个无边界循环里。

记录后段对“动态主义”和“组合主义”的讨论，是这一区分的新版本：

- 大规模、机械式维护任务，可以使用代码化、可复现的模板 Flow。

- 需要频繁介入、不断出现新信息的探索任务，可以少加一些固定枷锁，让 Agent 动态决定下一步。

固定 Flow 的问题，是无法预见开发途中出现的所有情况；完全动态的 Flow 则不利于人理解，可能在“主 Agent 大包大揽”和“子 Agent 无限递归”之间摇摆。参与者最后明确说，自己仍在两种模式之间交互式切换，还不知道自动取得平衡的机制是什么。

## 八、没有例证的 Flow 站不住脚

社群对方法论有一个很强的自我约束：不能只靠架构图、漂亮术语和 Token 数量证明有效。

五月底，群里提出：“没有例证的 Flow 是站不住脚的。”所谓例证，不是让同一个 Agent 给自己的设计打分，而是在真实的第三方项目、真实规模的任务中，展示它怎样改变了质量、时间、成本或人的介入程度。

这也解释了为什么聊天里那些惊人的数字需要谨慎阅读：22 个 Agent、4.7 万行增量、每小时一万行、101 个 Agent、几十小时持续运行、把二十多万行代码删到九万行——它们首先说明“这种规模的行为已经可能发生”，同时也暴露成本、审查与可维护性问题。代码行数既不是质量本身，删除量也不是简洁性的充分证明。

Flow 的 Benchmark 很难做，原因在记录中说得很清楚：

- 单个 Prompt 太短，无法代表多小时、多阶段的任务。

- 完整任务成本过高，难以做大量消融实验。

- 模型版本、推理强度、工具和基础设施变化太快，同一 Flow 的效果会漂移。

- 模型可能针对可见指标“刷分”，隐藏验证又增加实验成本。

- 质量、耗时、Token、人类介入次数和可理解性往往互相牵制。

因此，群里一方面想把 Flow 拆成原语，做 Micro-benchmark 和 Profiling；另一方面又坚持最终仍需长程、真实、产物级的验证。这个张力一直没有消失。

## 九、记忆不是越多越好，而是要承担路径依赖

关于 Agent Memory，聊天记录里的总体情绪相当谨慎。

早期并行实践强调“Zero Shared Memory for Sub-agent”：不同 Agent 不应共享完整 Session History，但可以共享经过整理的 Curated Knowledge。这样既保留独立性，也不必让每个 Agent 重新发现所有事实。

群友对自动记忆的主要担忧有四类。

第一，记忆会过时。代码、依赖、实验结论和项目目标都在变化，昨日正确的规则可能在今天阻塞新路径。

第二，记忆会放大偶然经验。一个 Agent 在某次失败后写下的总结，可能不是事实，只是当时实现有误；后来所有 Agent 都把它当成真理。

第三，记忆的优先级可能过高。自动修改 `CLAUDE.md`、`AGENTS.md` 或高优先级 Rule，相当于让正在工作中的 Agent 改写下一轮的思维边界，容易造成膨胀和投毒。

第四，记忆会减少探索。群里有一句非常反直觉的话：“好的记忆极其有毒性，会让 Agent 停止路径探索。”这里的“好”是指曾经成功的路线；它最容易让系统产生“既然上次有效，就不要再看别处”的惯性。

六月的一次实验更具体。一个优化 Flow 每轮把失败尝试写进错题本，结果反而更差，因为巨大的性能提升有时就在失败尝试附近；Agent 把“这次没做对”误读成“这个方向不可能”。讨论中提出 Evidence Score 与 Decay Rate，让经验有证据权重并随时间衰减，但该项目最后采用的方案是干脆删除错题本。

对 GraphRAG、向量库和复杂外置记忆，也有参与者报告“不如文件加 grep/rg”。这只是具体项目经验，不足以否定所有知识图谱；它提醒的是，记忆系统本身有维护成本，索引与正文之间还会发生双写漂移。

记录后段出现了几种并存的实践：

- 只保留项目特有、代价很高的坏经验，并设置很低的触发频率。

- 维护一个人和 Agent 都能读的 SSOT、项目 Spec、目录 README 或文档索引。

- 不保存长期 Memory，每次让 Agent 重读完整项目 Spec；有群友接受约五万 Token 的固定开销，换取简单和可靠。

- 在多人协作里使用更细的文档结构，因为“每次重读全部”不再可行。

- 对大量领域 Skill 做 Progressive Disclosure，甚至做 Skill Dropout，随机不加载一部分，避免流程过度固化。

- 让多个探索 Agent 互相独立，由上层根据对比结果判断什么值得沉淀，而不是让 Worker 自己总结自己。

所以，记录里的 Memory 更接近一种**带证据、带时效、可追溯的剪枝机制**，而不是“把过去所有对话都保存下来”。

## 十、Human in the Loop，后来变成了 Human Harness

随着 Agent 产出速度增加，一个尖锐的问题逐渐浮现：如果生产力扩大一百倍，人类怎样让自己的掌控度也扩大一百倍？

群里没有找到让人脑同步扩容的方法。启动十个 Loop 很容易，但一个人一天只有有限的有效注意力。有人报告自己一天最多照看约十个 Loop 与 Goal，每个项目每天只分到一次介入或观察的机会；再继续扩展，人的角色就会退化成不停 Approve，既不了解系统，也无法为结果负责。

因此，讨论从“Agent Harness 让 AI 更强”走到另一句话：

> Human Harness 让人类更负责。

HAD（Human Aided Design）也在这个语境中被提出：把人类有限的带宽和脑力，放在 Agent Workflow 精心挑出的确认点上。Agent 不只要完成任务，还要维持一个“人类保险”——让使用者知道关键决策是什么、哪里存在不确定性、哪些后果需要人承担。

“层级抽样测试”是一次具体尝试。长程任务中的 Agent 定期给人出 Quiz，检查三件事：人是否还记得自己的原始设计；Agent 的设计是否被人真正理解和认可；人是否缺少理解当前决策所需的背景知识。到了记录末段，这个想法又被重新提出为：长程 Agent 应主动以考试形式和人对齐。

反对意见同样强烈。有人认为 Quiz 违反人性，最后只会成为安慰剂；如果 Plan 本身充满黑话，考试并不会恢复理解；抽样也可能刚好漏掉真正危险的深层决策。正确做法有时不是答题，而是在第一次看不懂时就停下来，与 Agent 把术语和决策掰扯清楚。

聊天里也给出了一种更朴素的“可读性测试”：生成一份单独面向人的文档，要求每一行使用的变量都已在前文定义，维护一份领域术语表，再让一个完全没有上下文、只能读文档、不能看代码的 Agent 标出所有看不懂的地方。重复几轮后，文档通常会更接近人能读懂的版本。代价是速度很慢，而且术语表本身也会过时；它解决的是表达层，不等于人已经理解了所有实现细节。

讨论最后出现了一个更务实的风险分层：认知债不可能完全消失，要看潜在损失。低风险、可回滚的任务可以后置学习；账本、安全、自动驾驶式的高损失任务必须在关键边界上先讲清楚，必要时退回到更受控的补全、骨架和人工验收方式。

记录后段还有一句更直接的提醒：不要把 Thinking 外包。模型之间的能力差距也许会变化，但人如果只是不断 Approve，系统迟早会变成自己无法理解、出问题后也无法快速止血的“歼星舰”。人可以少写代码，却不能在目标、架构、优先级、收益损失和批判性判断上一起偷懒。

## 十一、当模型开始“内化 Harness”

从五月到七月，讨论里反复出现一个判断：真正有效的 Harness，会被产品做成内置功能，进一步被模型训练成默认行为。

早期需要外部 Flow 强制的 Builder—Reviewer Loop、任务追踪、短期记忆、主动分解和子 Agent 调用，在新模型上逐渐自发出现。七月有参与者观察到，模型会自己规划、拆依赖、启动大量对抗审查，并且像 Humanize 一样“按着自己不让自己完成”。有人据此说“模型把 Harness 都内化了”，甚至认为 Humanize 的部分历史使命已经完成。

这仍然是社区判断，不是对模型内部机制的证明。但它确实改变了外部 Harness 的位置：

- 在日常生产力任务里，复杂外部 Flow 可能变成重复指导，甚至干扰已经学会该行为的模型。

- 在实验任务里，外部 Harness 仍可作为受控缰绳，管理网络、多模态、预算、沙箱、权限和消融开关。

- 在多人协作里，外部系统仍要负责产物、交接、审计和责任边界。

- 在高风险环境里，不能因为模型“通常会做”就删除机械门禁。

模型内化编排还带来了新的不透明。聊天记录里有人遇到后台临时任务读取浏览器上下文，却不显示为普通活动 Session；也有人发现应用会悄悄启动子 Agent。即使没有发生写入，这类行为也说明：当编排从外部脚本进入模型和产品内部，可观测性、权限提示、预算归属和任务列表必须跟上，否则用户只会感觉系统“闹鬼”。

七月底，群里同时出现了两种看似相反的实践。

一种是返璞归真：裸 Pi、极短 System Prompt，只留 Bash、Sub-agent，甚至不使用长期 Memory。强模型自己现场造工具，人只需要说明任务并要求使用子 Agent 做实现与审查。支持者报告 Token 更省、体验更快，但这仍是个人条件下的结果。

另一种是更明确的角色分工：三个主 Session 分别负责 Arch、PM、Audit，每个再带三到十个子 Agent。人主要与 Arch 讨论并生成“会议记录”；PM 只从成熟部分挑切片、派发到 Worktree 并合并；Audit 阅读 PM 的执行轨迹，把被跳过或不合理的部分写成“会议缺陷”，再交回人和 Arch 讨论。

这并不是早期“虚拟公司”叙事的简单回潮。每个角色的权限、输入、输出和不做什么都被收得很窄；角色之间主要通过文件和审计轨迹连接，而不是自由开会。它说明一个更稳妥的结论：**最小 Harness 与显式组织结构都可能有效，取决于任务、模型、风险和协作规模。**

## 十二、星舰之后，简化本身成为一项 Agent 能力

记录末尾，Agent 不只被用于 Build，也越来越多地被用于删除、重写和简化。

有参与者报告，模型在代码完成后继续阅读几十个文件，主动提出更凝练的解法并重写；也有人用一个模型 Build，再用另一个模型 Review 和“铲屎”，把项目从二十多万行逐步缩到更小规模。这些报告让群里感叹：几个月前还很难相信模型能“正确删除代码”，现在简化正在变成一种可调用的能力。

但这里仍有明显风险。模型可能删掉二万行，又为了兼容、验证和防御新增三万行；它可能口头宣称移除了炮塔和装甲，随后又在自我审查中把同等复杂度加回来。测试通过也不代表删除方向正确，因为测试只覆盖已表达的约束，而人知道哪些错误更可能发生、哪些地方更重要、哪些失败可以接受。

因此，记录中出现了几种约束简化的办法：

- 在任务完成后单独调用 Simplify 与 Verify，而不是让 Build 无限扩张。

- 用奥卡姆、SSOT 和“事前凝练，事后清 Slop”表达方向，但不要只依赖 Magic Words。

- 明确删除兼容层、历史文档和回退逻辑是否真的符合项目阶段。

- 让 Reviewer 检查“为什么存在”，而不是只检查“是否能运行”。

- 把需要标准化的工程接口做成 Tool 或表格约束，让 Agent 做“填空题”，而不是让它自由改依赖、Fork 上游甚至修改操作系统来绕过限制。

简化并不是少写几行代码，而是恢复任务的真正命题：哪些结构服务于当前需求，哪些只是 Agent 在多轮迭代中给自己加的戏。

## 十三、反复出现的共识，与仍未解决的分歧

严格说，聊天记录里很少有所有人一致同意的结论。但以下原则在不同时间、不同项目里反复出现：

1. 先定义目标、边界、验收标准和不可逆决策，再扩大自动化。

2. 并行首先服务于上下文隔离和假设多样性，不服务于 Agent 数量展示。

3. Build 与 Review 最好分开，独立上下文往往比同一上下文自评更有价值。

4. Agent 之间优先通过可审查的产物协作；自由对话必须有明确理由。

5. 权限边界尽量用工具和程序实施，不只写在 Prompt 里。

6. 确定、机械的规则交给脚本、Hook、测试和静态检查；Agent 用在需要判断的地方。

7. Flow 要有可观察状态、预算、停止条件、回滚点和异常回收。

8. 构建、维护与探索不是同一种任务，不应默认共用一套 Flow。

9. Memory 应被整理、验证、衰减和追溯，不应等同于完整历史。

10. 每次模型能力变化后，都要重新测试原有 Skill 与 Flow；旧方法可能从增益变成干扰。

11. 方法论必须有真实例证，并同时看质量、时间、Token、人类介入和可理解性。

12. 人可以把执行外包给 Agent，但不能把责任、判断和后果一起外包。

而下面这些问题，直到记录结束仍然没有唯一答案：

| 问题 | 一端 | 另一端 | 记录中的状态 |
| --- | --- | --- | --- |
| Agent 是否应直接通信 | 平级沟通可以纠错、碰撞新想法 | 对话带来陈旧信息、噪声和不可见决策 | 构建任务偏向隔离与产物；探索任务保留例外 |
| Flow 应固定还是动态 | 固定 Flow 可复现、可审计、可调度 | 动态 Flow 能响应途中出现的新信息 | 参与者仍在两种模式间手工切换 |
| Harness 应做多重 | 显式结构能提供边界和保证 | 强模型会内化结构，重 Harness 可能反而干扰 | 默认趋向简单，高风险与实验环境保留控制层 |
| 是否需要长期 Memory | 记忆减少重复发现，支持交接 | 记忆会过时、投毒并制造路径依赖 | 倾向 Curated Knowledge、SSOT、衰减与渐进披露 |
| 人应介入多少 | 介入保证理解与责任 | 人的注意力是扩展瓶颈 | 按损失分层；关键决策介入，低风险任务后置学习 |
| 多 Agent 是否优于单 Agent | 并行能分治、隔离上下文、增加候选 | 同模型多开可能只是更多采样和重复劳动 | 必须看任务耦合度、模型差异和评估方式 |
| 评价 Flow 看什么 | 长程真实项目最可信 | 全量实验太贵、太慢、难消融 | Micro-benchmark 与真实例证并行存在 |
| 管理学还是编程语言 | 角色有助于人理解职责 | PL/IR 更适合表达权限、状态和检查 | 两种语言都保留，但都必须落到真实约束 |

## 结语：Agent 系统最后仍然在问“谁来负责”

如果把这几个月的讨论压缩成一句话，它不是“应该开多少个 Agent”，也不是“哪一种 Flow 最强”。它问的是：

**人的意图怎样进入系统，Context 怎样被切分，权限怎样被限制，证据怎样被保留，偏离怎样被发现，任务怎样停止，以及最后谁为结果负责。**

Humanize 最早依靠一个简单的 Build—Review Loop，把 Agent 从一次性生成推向长程收敛；随后社群又不断拆解这套 Loop，加入并行、隔离、语言、运行时、记忆、动态 Flow 和 Human Harness。模型能力增强后，一部分结构被模型吸收，复杂方法又开始回到 Bash、Sub-agent 和极短提示。与此同时，角色分工、审计、标准化与多人协作又以更明确的边界重新出现。

这段记录真正留下的，可能不是一张最终架构图，而是一套仍在生长的判断语言：PDBR、禁止沟通、Context Isolation、Artifact-centered、Human Harness、认知债、Flow as Code、动态主义与组合主义、星舰与船坞。

它们共同提醒我们：Agent 越能干，越不能只看它“做了多少”。
