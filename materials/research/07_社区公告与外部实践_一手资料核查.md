## 1. Humanize 1.0：把判断放进可重复的循环

**项目事实**：

- [PolyArch/humanize](https://github.com/PolyArch/humanize) 当前 README 将项目
  定义为带独立 AI Review 的迭代开发插件；RLCR 由 Claude 实现、Codex 独立
  Review，问题再反馈给实现阶段，直到达到验收条件。
- README 明确写出“人类必须保持 Architect”以及执行前理解 Plan 的要求，说明
  计划接受和执行循环从一开始就被分开处理。
- [PR #159：add coach mode to gen-plan](https://github.com/PolyArch/humanize/pull/159)
  于 2026-05-13 创建、2026-06-13 合并。PR body 明确记录了 `--coach`、强制阶段
  Quiz、理解检查、Coach Ledger 和写入 Plan 前的最终人工接受；答错按设计意图
  漂移、AI 设计修正或背景知识缺口分类。这个 Pull Request 是 Coach Mode 史料
  中最直接的公开证据。

**可用于正文的设计提炼**：

1. Humanize 的核心单位不是一次 Completion，而是“Plan → Build → Summary →
   Review → Revise”的闭环。Reviewer 判断的是目标是否继续被推进，不能只看
   最新 Diff 是否看起来合理。
2. 人类判断被放在循环的入口：目标、验收标准和证据先说清楚，后续模型才有
   可以反驳的边界。Coach Mode 将“我同意这个 Plan”进一步变成“我能解释并
   复述这个 Plan”。
3. 这使 Human Harness 有了一个清晰的解释：它不替人做决定，负责把需要人
   承担的决定提到合适的时间和材料面前。

这里的版本、Star 数和可用命令会变化，正文应链接仓库和 PR，不要把当前数字
写成历史定论。

  当前仓库 README 以 `omh` 为主命令，`omp` 只保留兼容别名；这能解释公告
  中“detach 之后在 humanfia 维护”的说法。

### 2.2 对 Human Harness 有用的运行时设计

当前 [README 的 Workflow Orchestration 部分](https://github.com/humanfia/oh-my-humanize#workflow-orchestration-advanced)
和 [`docs/workflows.md`](https://github.com/humanfia/oh-my-humanize/blob/main/docs/workflows.md)
给出了比公告更具体的控制语义：

- `.omhflow` 是可分发的 Flow Artifact；开发阶段可以编辑，生产 Attempt
  运行在不可变 Freeze 上。
- 需要变更时，操作员要先停止运行、保存 Checkpoint、批准变更、冻结新图，
  再从 Checkpoint 重启。Flow 的变化因此留下了可追踪的责任边界。
- TUI 的 Workflow Dashboard 用来观察、Steer、Interrupt、Stop、Restart 和
  Change；Humanize RLCR 和 KDA 当前以 `experimental::` 候选 Flow 运行，
  需要长期实证后才能晋升为稳定 Built-in。
- `task` 将任务分到隔离 Worktree，返回经过 Schema 验证的结果；README 还
  描述了独立 Reviewer Model、LSP、Debugger、可持续 Python/Bun 工具和
  Stream Rule。这些组件把“长期执行、可恢复、可审计”从 Prompt 习惯变成了
  Runtime 能理解的对象。

这些信息可以支持 H3 章节中的一个判断：Dynamic Workflow 的关键不是让 Agent
拥有更多自由，而是让 Flow、状态、权限、Checkpoint 和人工介入成为同一套
运行时语义。README 中的“40+ providers”“55k lines of Rust core”等是项目
自报指标，只能作为当时版本的宣传快照，不能当作独立 Benchmark。

## 3. ai-usage：把 Token 消耗变成可观察的工程数据

项目：[SihaoLiu/ai-usage](https://github.com/SihaoLiu/ai-usage)。截至核查日，
仓库 README 和 `docs/usage.md` 明确支持：

- Claude Code、OpenAI Codex、Gemini CLI、Kimi Code 和 Oh My Pi 的本地使用量
  汇总；
- 按模型分解 Token、费用估算、日/周/月投影，终端实时监控和 CPU/RSS 遥测；
- `ai-usage snapshot --days 7 --tool all` 输出带 `schema_version`、时间范围、
  `daily` 和 `top_models` 的机器可读 JSON；
- 读取各工具写在本地的 JSONL/JSON 会话日志，也支持按 `host`、`tool`、`session`
  筛选；可选的同步服务把多个机器的归一化记录合并起来。

源码中的归一化结构把一次记录拆成 `input_tokens`、`output_tokens`、
`cache_read_input_tokens`、`cache_creation_input_tokens` 和
`reasoning_output_tokens`，并保留 `model`、`effort`、`session_id`、时间和费用。
这比把所有数字简单相加更适合分析 Humanize：新输入、缓存命中、推理输出和
真正生成的文本，对成本和认知负担的含义不同。

**对本册 Token 统计的边界**：

- 公开仓库只能证明“工具如何读取和归一化本地日志”，不能直接证明群里某个人
  的消耗量。要做按成员统计，必须拿到脱敏后的个人快照，并建立成员、机器、
  Session 的映射。
- 文档把 API Cost 标成估算值，模型价格通过内置表、缓存和 LiteLLM 分层解析；
  因此正文应同时展示 Token、Cache Hit、模型、时间段和成功/返工状态，不能只
  用美元数给人排序。
- 统计时最好保留“总上下文”“新 Prefill”“Cache Read”“Decoding/Reasoning”
  四个维度，并把人类介入时间、Review 轮数和任务是否通过验收一并记录。这样
  Token 数据才会成为 Harness 的效率证据，而不是排行榜。

资料入口：
[README](https://github.com/SihaoLiu/ai-usage/blob/main/README.md) ·
[Usage 数据源与 JSON Snapshot](https://github.com/SihaoLiu/ai-usage/blob/main/docs/usage.md) ·
[跨机器同步模型](https://github.com/SihaoLiu/ai-usage/blob/main/docs/sync.md) ·

## 4. Multi-Agent Wiki：为 Humanize 的实践提供模式坐标

### 4.1 资料身份

- [网站首页](https://multi-agent.wiki/) 和可直接读取的
  [`/index.md`](https://multi-agent.wiki/index.md) 将其定义为多 Agent 交互模式、
  分类、工作流编排和工程实现的知识库，而非论文综述或框架宣传页。
- 网站列出 30 个模式、7 个分类、Dynamic Workflow 专题和 6 个实现指南；
  [GitHub 源仓库 README](https://github.com/fuergaosi233/multiagent-explorer#readme)
  给出了同样的内容结构和可运行的 Mermaid 可视化。

### 4.2 可以直接对应 Humanize 的模式

网站的 [Taxonomy](https://multi-agent.wiki/taxonomy.md) 不是按框架名称分类，
而是拆成控制结构、工作流编排、信息流、决策方式、执行环境和协议连接：

- Humanize 1.0 的 Builder—Reviewer—Ralph Loop 对应
  `Generator-Critic`、`Refinement Loop` 和 `Human-in-the-loop`；
- Humanize 2.0 的可编排 Flow 对应 Graph/State Machine、Typed Artifact 和
  Blackboard/Shared State；
- Humanize 3.0 的 Flow 运行中变化对应 Dynamic Workflow、Parallel
  Fan-out/Gather、Verifier、Worktree Isolation 和 Checkpoint/Resume；
- Coach Mode 则对应 `Clarification-at-edge` 和
  `Human-in-the-loop`：人的输入不应只作为最后的批准按钮，而要回写成
  Agent 状态的一部分。

这是一套解释坐标，不是说 Humanize 当时直接采用了该 Wiki 的实现。

### 4.3 对长程 Agent 最有价值的几条原文规则

- [Decision Matrix](https://multi-agent.wiki/decision-matrix.md) 将“长而复杂的
  任务”放在 Graph Workflow + Task Registry，将“代码库级审计”放在 Dynamic
  Workflow + Parallel + Verifier + Worktrees，将高风险操作放在人类审批和
  Guardrails 之后；需要中途签字时，拆成多个带 Gate 的 Workflow。
- [Dynamic Workflow / Code-Orchestrated Subagents](https://multi-agent.wiki/patterns/dynamic-workflow-code-orchestration.md)
  把 Plan、循环、分支、Fan-out、验证和中间状态放进脚本，Worker 只做具体
  读取、修改和工具调用；独立 Verifier 先尝试证伪，再进入合成。
- [Human-in-the-loop](https://multi-agent.wiki/patterns/human-in-the-loop.md)
  要求按 `read / write / shell / network / deploy` 等风险分级，并让审批卡展示
  动作、原因、范围和回滚方案；反馈必须进入 Agent 状态，而不能停留在聊天
  外部评论里。
- [Observability and Event Model](https://multi-agent.wiki/implementation/observability.md)
  建议记录 Workflow、Phase、Agent、Claim、Checkpoint 多层事件，并关注任务成功率、
  Verifier 拒绝率、每个任务成本、人类审批延迟和上下文压缩率。

### 4.4 与 Coach Mode 的接法

可以把它当成一张“讨论前的地图”：先用 Taxonomy 判断当前 Flow 的控制权、
状态和风险，再用 Decision Matrix 选择并发、验证、隔离和审批方式，最后由
Coach Mode 逐项要求人复述“谁在什么时候拥有哪种权限、证据在哪里、失败怎样
恢复”。这样人类理解检查有了可观察的对象，Human Harness 也不必把所有判断
压缩成一个泛泛的“你理解了吗”。

### 5.1 Humanize 1：From Agentic Flow to Judgement Engineering

链接：
[Humanize 1 PDF](https://drive.google.com/file/d/1bvQl_IE1JyXqW6NkSMFPrs_G0erAdgca/view?usp=sharing)。

核验到的文件信息：标题为 `Humanize — PolyArch design system`，60 页，创建时间
为 2026-04-25 22:29（PDF 元数据）。演讲中最值得作为正文线索的内容包括：

- GAAC 的五阶段工程机（Research、Architecture、Planning、Implementation、
  Close）被认为产生了过多角色和交接税；Humanize 选择保留最小的
  Builder—Reviewer 判断循环。
- Plan 被称作 Loop 的 Constitution；目标、非目标、可观察的 Acceptance、
  Constraints、Milestones 和 Risks 让长期运行有可证伪的停点。
- 人类仍是 Architect，执行前的 Plan Understanding Quiz 是低成本的摩擦；
  演讲同时把它描述为“Advisory”，与后来 PR #159 中更强的 Coach Gate 形成
  了清楚的演进关系。
- Builder 阶段只用结构化 Summary 作为接口，Review 阶段才读 Diff；P0–P1
  阻断、P2–P9 排队，Full Alignment Check 周期性回看原始 Plan。
- BitLesson 作为项目记忆，选择器按当前目标、触碰文件、上次 Review 和前置
  条件筛选；Delta Card 用机械检查核对“声称改了什么”和“磁盘真正改了什么”。
- 演讲把人类参与分成 Watchtower、Checkpoint、Co-pilot、Handoff 四种模式，
  并强调人类介入是一个旋钮，不是一开一关的总开关。

这些观点可以补充 README 的 Human Harness 段落：Coach Mode 的价值在于安排行
为人类准备的判断材料，减少人逐 Token 追踪的负担；判断仍由人负责。

### 5.2 Humanize 2：From a Flow That Works to a Platform for Building Flows

链接：
[Humanize 2 PDF](https://drive.google.com/file/d/1j-Xxtwf5GQ5PYcJ8Glnd6XOKNuizUNbl/view?usp=sharing)。

核验到的文件信息：标题为 `Humanize 2 · From a Flow That Works to a Platform for
Building Flows`，18 页，创建时间为 2026-05-17 13:38（PDF 元数据）。演讲稿把
H1/H2/H3 的关系说得非常集中：

- H1 是“一条能工作的 Flow”；H2 是“人类构建 Flow 的平台/语言”；H3 是
  “Agent 能在 Flow 上构建 Flow 的自动化系统”。
- H2 保留 H1 的 RLCR 语义，新增 HTML Cartridge、触发式 Dataflow Executor、
  MCP Hub 和本地 GUI；Flow 从硬编码脚本变成可编辑、可观察、可组合的数据。
- Cartridge 由 Manifest、State、Templates、Flow、View 五个区域组成；12 类
  Vertex 覆盖 Agent、Human、Script、Check、Transform、Message、Branch、Loop、
  Parallel、End、Await 和 Sleep。
- 状态分成一次交付的 Immutable Artifact 和可由 JSON Patch 更新的 Mutable Board；
  Vertex 等待输入到齐后被唤醒，调度关系由数据和触发条件决定。
- 案例页把并行探索、运行时 Captain 动态派生 Worker、Session Tree、Dashboard
  和可编辑的 Flow 放在一起，明确把运行中观察和干预当作平台能力。
- H3 的方向是 Agent 生成、部署和改写 HTML Cartridge；这属于路线叙事和原型
  目标，不能写成已经全面实现的产品事实。

H2 幻灯片可以作为 README 中“Flow 逐渐成为一等对象”的历史证据；真正的实现
状态仍应以仓库提交和 `oh-my-humanize` 的工作流文档为准。

## 6. 知乎文章：把 Humanize 放进一次真实的 GEM5 改造

文章：[《Humanize：一个 prompt 重构 GEM5 的构建系统》](https://zhuanlan.zhihu.com/p/2011939681307206316)。
知乎直链在当前网络环境返回 403，使用文本代理读取到了文章正文；页面署名
`ChiveArchitect`，显示 97 个赞，编辑时间为 2026-03-03。它属于作者公开经验，

### 文章可以直接支持的设计观察

- 文章把 Humanize 概括成：先生成可量化、可验证的设计目标，再由一个 Code
  Agent 实现，另一个 Review Agent 批判，多轮迭代直到目标完成且 Review 没有
  发现潜在 Bug。
- 文章认为大型项目的问题不止是模型能力，还包括上下文和生成并发度；Team/
  Swarm Mode 让主 Session 少装一些中间结果，降低 Compaction 压力。
- 文章强调 Claude 和 Codex 的模型差异可以转化成 Review 互补：一个负责实现，
  另一个专门找遗漏和过度声称。这可以作为 Humanize “独立 Review”设计的
  社区体验证据，但不能推导出所有任务都应该用两个特定模型。

### Token 数字和工程案例的证据等级

- 作者自述过去 48 小时使用约 1.13B Token，其中 1.07B 为 Prefix Cache Hit、
  60M Prefill、2.4M Decoding，并按当时 API 价格估算约 660 美元。这些数字
  没有附带可复算的日志，适合说明长程 Agent 的成本量级，不适合作为社区平均
  数据或个人排行榜。
- 文中 GEM5 案例链接到
  [`gem5/gem5#2969`](https://github.com/gem5/gem5/pull/2969)。截至核查日，
  GitHub PR API 显示该 PR 仍为 Open，由 `SihaoLiu` 从 `PolyArch:develop-scons-to-cmake`
  提交，133 个 Commit、567 个改动文件、26,491 行新增、16,476 行删除；PR
  描述列出 CMake+Ninja 与 Bazel、代码生成流水线、CI、单元测试和二进制一致性
  检查。这些是 GEM5 PR 的项目事实，文章“Humanize 参与改造”则属于文章
  叙述，两层证据需要分开写。
- 文章还提到纯 Codex Skill、`gen-plan` 使用通用模型、Coding 使用 Codex 模型
  等细节。这些是 2026-03-03 的个人配置经验，后来模型名、仓库组织和命令都
  可能变化，正文引用时应保留日期。

## 8. 可写入 README 的证据链

如果要给 Coach Mode 增加一小段外部参照，可以把资料压成下面这条链：

```text
Humanize 1.0 / PR #159
  → 入口处的 Plan 理解与人工接受
  → Humanize 2.0 幻灯片的 Typed Artifact、Board、Trigger 和可观察 Flow
  → oh-my-humanize 的 Freeze、Checkpoint、Approval、Worktree 与 Runtime Dashboard
  → Multi-Agent Wiki 的 Verifier、HITL、Dynamic Workflow、Observability 坐标
  → ai-usage 的 Token / Cache / Cost 数据
  → 人类可以解释、反驳并承担结果，Agent 才继续长程运行
```

这里有三个需要在正文中明确的边界：

1. 项目 README 和 PR 证明实现或接口；幻灯片、知乎、公众号文章记录的是当时
   的设计叙事和实践经验，不能互换证据等级。
2. GitHub Star、模型名、价格和仓库地址都是时间敏感信息，正文应写日期并链接
   原始页面；不把当前快照当成历史事实。
3. Token 统计应以脱敏后的本地日志为准，并同时保留任务成功、返工、Review
   轮次和人类介入；单独比较某个人烧了多少 Token，会把探索、缓存和无效循环
   混在一起。
